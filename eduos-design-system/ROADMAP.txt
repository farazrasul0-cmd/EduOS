 LOCALE LOCK (Bangladesh) — applies everywhere below
 -------------------------------------------------------------------------------
 - Currency .... Bangladeshi Taka. Code BDT, symbol ৳. Format ৳4,500.
                 (Optionally support the South-Asian lakh/crore grouping,
                 e.g. ৳1,00,000 = 1 lakh — confirm with first school.)
 - Language .... BILINGUAL from day one: English + Bangla (বাংলা), both fully
                 supported at launch (not English-first). Per-user language
                 toggle, persisted. Every user-facing string goes through i18n
                 — no hardcoded text. Applies to UI, emails, SMS, and PDFs.
 - Payments .... Mobile Financial Services: bKash, Nagad, Rocket, Upay, plus
                 cards/banks via an aggregator (SSLCommerz / aamarPay /
                 ShurjoPay). NOT Stripe/Razorpay (limited/again unavailable in BD).
 - SMS ......... Local gateways via aggregators (SSL Wireless, MIMSMS, bulksmsbd,
                 Banglalink/GP/Robi masking). Twilio works but is pricier.
 - Hosting ..... Pick a low-latency region for BD users (AWS ap-south-1 Mumbai
                 or ap-southeast-1 Singapore). Consider data-residency wishes.
 NOTE: the prototype currently shows Indian Rupee (₹). All ₹ -> ৳ in production
 (in seed data, KPI tiles, fees, invoices, formatting helpers).

 THE GAP TO PRODUCTION (in one line)
 -------------------------------------------------------------------------------
 Turn 11 static, mock-data mockups into a real multi-user, multi-school SaaS:
 a typed frontend with a build pipeline, a backend + database, authentication &
 roles, real CRUD for every feature, payments, messaging, file uploads, the AI
 exam builder, testing, security, hosting, monitoring, and a launch plan.

 HOW TO READ THIS FILE
 -------------------------------------------------------------------------------
 Phases are roughly sequential, but several run in parallel once the foundation
 (Phase 0-2) is in place. Each phase lists: GOAL, TASKS, and DONE-WHEN. Don't
 skip Phase 0 — most pain later comes from decisions not made up front.


===============================================================================
 PHASE 0 — DECISIONS & FOUNDATION  (week 1)
===============================================================================
 GOAL: Lock the stack and ground rules so we never re-litigate them mid-build.

 [ ] Pick the frontend stack
       - React 18 + TypeScript + Vite (reuse Desktop\eduos scaffold).
       - Routing: React Router (or TanStack Router).
       - Styling: Tailwind, seeded from colors_and_type.css tokens.
       - Data fetching/cache: TanStack Query.
       - Forms + validation: React Hook Form + Zod.
 [ ] Pick the backend stack (choose ONE, write down why)
       - Option A: Node + TypeScript (NestJS or Fastify) — shares language w/ FE.
       - Option B: Python (FastAPI/Django) — strong if team knows Python.
       - Option C: Supabase / Firebase — fastest MVP, less control.
 [ ] Pick the database
       - PostgreSQL (recommended: relational data, multi-tenant friendly).
       - ORM: Prisma (Node) or SQLAlchemy/Django ORM (Python).
 [ ] Pick hosting / infra targets
       - Frontend: Vercel / Netlify / Cloudflare Pages.
       - Backend + DB: Railway / Render / Fly.io / AWS (RDS + ECS) / Supabase.
       - File storage: S3 / Cloudflare R2 / Supabase Storage.
 [ ] Pick supporting services  (Bangladesh defaults in brackets)
       - Auth: Clerk / Auth0 / Supabase Auth / self-rolled (JWT + bcrypt).
       - Email: Resend / Postmark / SES.
       - SMS: [SSL Wireless / MIMSMS / bulksmsbd via masking gateway];
              Twilio as fallback. Many BD schools rely on SMS over email.
       - Payments: [SSLCommerz or aamarPay/ShurjoPay aggregator] to accept
              bKash, Nagad, Rocket, Upay + cards/bank. (No Stripe/Razorpay.)
       - AI: Anthropic Claude API (for the AI exam builder).
 [ ] Repository & workflow
       - Monorepo (apps/web, apps/api, packages/ui, packages/types) via pnpm
         workspaces or Turborepo — recommended so types are shared.
       - Git: trunk-based or GitHub flow; protected main; PR reviews required.
       - Conventions: ESLint + Prettier, commit lint, .editorconfig.
 [ ] Environments
       - local / staging / production. One .env per env; NEVER commit secrets.
       - Secrets manager (Doppler / Vault / platform env vars).

 DONE-WHEN: every bullet above has a written decision in /docs/decisions
 (ADRs), the monorepo is initialised, and `pnpm install` works clean.

===============================================================================
 PHASE 3 — DATA MODEL, BACKEND & AUTH  (week 3-6)  [core backend]
===============================================================================
 GOAL: A secure API with a real schema and role-based access.

 [ ] Model the domain (Postgres schema + ERD). Core entities:
       School (tenant), User, Role (teacher/admin/parent/student),
       Class/Section, Student, Guardian/Parent, Subject,
       AttendanceRecord, Assignment, Submission,
       Exam, Question, Result/Mark, GradeScale,
       FeePlan, Invoice, Payment,
       TimetableSlot, CalendarEvent, Message/Thread, Notification,
       AuditLog.
 [ ] Multi-tenancy strategy: row-level school_id on every table (+ RLS if
     using Postgres/Supabase). Decide shared-DB vs DB-per-tenant.
 [ ] Migrations tooling (Prisma migrate / Alembic). Seed script with the
     prototype's mock data so the FE has realistic content.
 [ ] Authentication: signup/login/logout, password reset, email verify,
     session/JWT, refresh tokens. MFA optional for admins.
 [ ] Authorization: RBAC + per-resource checks (a teacher only sees their
     classes; a parent only their child; admin sees the whole school).
 [ ] API layer: REST or tRPC/GraphQL. Generate/share types with FE.
 [ ] Validation on every endpoint (Zod/Pydantic). Consistent error envelope.
 [ ] Rate limiting, request logging, CORS, helmet/security headers.

 DONE-WHEN: a user can sign up, get a role, and the API enforces that role;
 schema migrations run on staging; seed data loads.

 PHASE 4 — FEATURE BUILD-OUT (page by page)  (week 6-14)
===============================================================================
 GOAL: Replace every mock page with real CRUD wired to the API.
 For EACH feature: API endpoints -> FE data hooks -> wire UI -> validation ->
 empty/loading/error states -> tests.

 [ ] Dashboard ...... real KPIs (student count, attendance %, pending fees,
                       upcoming exams), live charts, recent-activity feed.
 [ ] Students ....... roster CRUD, filter by class, add-student modal with
                       PROFILE PHOTO UPLOAD (already in prototype), student
                       detail/profile page (attendance/fees/marks history).
 [ ] Attendance ..... pick class+date, mark present/absent/late, bulk save,
                       live counts, notify-parent on absence.
 [ ] Timetable ...... weekly grid CRUD, per-class schedule, clash detection.
 [ ] Assignments .... teacher create/publish, student submission upload,
                       teacher grading + feedback, submission tracker,
                       notify parents toggle.
 [ ] Exams .......... exam list/CRUD, schedule, + AI builder (see Phase 5).
 [ ] Results ........ gradebook, enter marks, grade/GPA calc, publish,
                       report cards, PDF export.
 [ ] Fees ........... fee plans, invoices, status filter, mark-paid,
                       payment history, online payment (see Phase 5).
 [ ] Calendar ....... month view, event CRUD (PTM/holiday/exam/event),
                       filters, "up next".
 [ ] Parent messages  threaded teacher<->parent messaging (real-time, Phase 5).
 [ ] Settings ....... profile, school info, classes, notification prefs,
                       billing, integrations, security (password/MFA).

 DONE-WHEN: every page reads/writes real data, no mock arrays remain, all
 CRUD paths have happy + error + empty states.

       - Pre-signed S3/R2 URLs, size/type validation, virus scan, thumbnails.
 [ ] Notifications system
       - In-app (the bell dropdown) backed by a Notification table.
       - Email + SMS fan-out on key events (absence, fee due, results out).
       - Per-user preference center.

       - WebSockets (Socket.IO / Pusher / Supabase Realtime).
 [ ] Payments (Fees) — Bangladesh
       - Integrate an aggregator (SSLCommerz / aamarPay / ShurjoPay) so a

       - Webhooks/IPN -> mark invoice paid, generate ৳ receipt, handle
         pending/failed/refund states, reconciliation, settlement reports.
       - Store amounts in integer poisha/Taka minor units; format as ৳4,500.
 [ ] AI Exam Builder (Anthropic Claude API)
       - Inputs: class, subject, chapter, difficulty, #questions, marks.
       - Generate MCQ/short/long questions with answer keys; let teacher edit,
         regenerate, save to an exam, export PDF.
       - Add prompt caching; guard against prompt injection; rate-limit;
         track token cost per school. Human review before publish.
 [ ] Search + command palette (Cmd-K) — students/fees/exams global search.
 [ ] PDF generation — report cards, invoices, question papers.
 [ ] Internationalisation — BILINGUAL English + Bangla (বাংলা), required at
       launch. Wire react-i18next from the very first screen; extract ALL
       strings to en/bn locale files (no hardcoded text); per-user language
       toggle, persisted. ৳ currency + BD date/number formatting via Intl.
       Bangla-capable web font for UI AND a Bangla-embedding font for PDFs
       (report cards, invoices, question papers). Translate emails + SMS too.
       Add a CI check / lint that fails on missing translation keys.

 DONE-WHEN: each feature works end-to-end on staging with real services in
 test mode (test Stripe keys, sandbox SMS, etc.).

===============================================================================
 PHASE 7 — SECURITY & COMPLIANCE  (before public launch — NON-NEGOTIABLE)
===============================================================================
 NOTE: This product stores CHILDREN'S personal data. Compliance is mandatory.
 [ ] Data privacy law review (Bangladesh): track the BD Data Protection Act
       (draft/forthcoming) and the Digital Security / Cyber Security Act.
       Until BD law is final, adopt GDPR-style good practice as the baseline.
       - Parental consent flows, data-retention policy, right-to-delete.
       - If hosting data outside BD, confirm any data-localization expectations
         with schools and document it.
 [ ] Encryption: TLS everywhere; encrypt sensitive fields + backups at rest.
 [ ] Secrets hygiene; rotate keys; no secrets in client bundle.
 [ ] Authz audit — verify no cross-tenant / cross-role data leakage (write
       tests for "teacher A cannot read teacher B's class").
 [ ] OWASP Top 10 pass: injection, XSS, CSRF, IDOR, SSRF, auth flaws.
 [ ] Audit logging for sensitive actions (mark changes, fee edits, deletes).
 [ ] Dependency scanning (Dependabot/Snyk) + SAST in CI.
 [ ] Backups + tested restore; disaster-recovery runbook.
 [ ] Penetration test / security review before launch.
 [ ] Privacy policy + terms of service published.

 DONE-WHEN: security review signed off; backups restore verified; legal docs live.
